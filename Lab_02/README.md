# Ч3. Эксперимент с переполнением.

## Беззнаковый тип
* **Поведение:** Строго определено стандартом C++.
* **Механика:** Работает по правилам **модульной арифметики**. При превышении максимального значения число "перекручивается" (wrap-around) и становится равным нулю.
* **Объяснение:** В памяти все биты равны `1`. Прибавление `1` вызывает перенос во всех разрядах. Единица выходит за пределы разрядной сетки и отбрасывается, оставляя в ячейке памяти ровно нули. Для 32-битного `unsigned int` это переход `4 294 967 295 → 0`.

## Знаковый тип
* **Поведение:** По стандарту C++ является **неопределённым поведением (Undefined Behavior, UB)**.
* **Механика:** Аппаратно (из-за хранения чисел в дополнительном коде) прибавление единицы к максимуму (`0111...111`) меняет старший знаковый бит на `1` (`1000...000`), что превращает число в минимальное отрицательное. Для 32-битного `int` это переход `2 147 483 647 → −2 147 483 648`.
* **Почему это сделано намеренно:** Поскольку компилятор вправе предполагать, что UB никогда не произойдёт, он может просто "вырезать" проверку переполнения при оптимизации кода, и результат окажется не тем, что мы ожидаем увидеть.
  Чтобы продемонстрировать именно аппаратный wrap-around в отрицательную область, а не стать жертвой непредсказуемой оптимизации, переменная в коде помечена ключевым словом `volatile`.
  Это принуждает процессор честно выполнить операцию в памяти, игнорируя оптимизатор.

# Ч4. Эксперимент с точностью.

## Проблема сложения дробей
Компьютеры хранят числа в двоичной системе. В десятичной системе дробь `1/3` бесконечна (`0.3333...`). В двоичной системе такие числа, как `0.1` (т.е. `1/10`) и `0.2`, также превращаются в **бесконечные периодические двоичные дроби**.
Так как память ограничена (24 бита мантиссы для `float`, 53 бита для `double`, 64 бита для `long double`), эти бесконечные "хвосты" обрезаются. В результате в памяти хранится не ровно `0.1`, а его ближайшее двоичное приближение.

При сложении двух таких приближений ошибка накапливается. Если вывести результат `0.1f + 0.2f` с точностью до 20 знаков, мы увидим:
* `float`:        `0.30000001192092895508`
* `double`:       `0.30000000000000004441`
* `long double`:  `0.30000000000000000011`

Именно поэтому прямое сравнение `(0.1 + 0.2 == 0.3)` выдаёт `false` для всех трёх типов.

## Большие целые числа в `float`
Тип `float` занимает 32 бита, из которых на **мантиссу** (само значащее число) отведено только 24 бита. Это позволяет без искажений хранить лишь около **7 значащих десятичных цифр** (до `16 777 216`).

Если мы попытаемся сохранить большое число, например `123 456 789`, ему банально не хватит битов для точного представления младших разрядов. Процессор округлит его до ближайшего числа, которое может поместиться в мантиссу (например, `123456792.0`).

## Почему это критично для денег
Денежная сумма — это, по сути, число с **фиксированной** точностью: ровно 2 знака после запятой (копейки). Но `float`/`double` хранят числа с **плавающей** точностью, и большинство десятичных дробей (например, `0.10`, `0.20`, `0.57`) не представимы в двоичной системе точно.

Это приводит к двум проблемам:
1. **Ошибка накопления.** Если хранить баланс счёта во `float` и многократно прибавлять/вычитать копейки, ошибка будет расти. Например, сложение `0.01f` сто тысяч раз даёт не ровно `1000`, а `1000.0001...` (в коде это видно в разделе Part 4).
2. **Ошибка округления.** Сумма `1234.56f` в памяти хранится как `1234.5599365234...`. При округлении до копеек это может дать **не тот** результат, который ожидал пользователь.

## Как хранить деньги правильно
Деньги хранят в **целочисленном** типе — например, `long long`, где значение — это сумма **в копейках**. В нашем варианте `long long` вмещает до ≈ 9.2 · 10¹⁸ копеек (≈ 9.2 · 10¹⁶ рублей), переполнение практически исключено, а арифметика над целыми точна.

Вещественный ввод (`long double`) используется только один раз — при чтении суммы с клавиатуры, после чего сразу округляется до копеек через `llroundl(amount * 100.0L)` и переводится в `long long`.
